1. EXECUTIVE SUMMARY & CORE FINANCIAL GOVERNANCE MODEL
================================================================================

The CST White Label (eBricks) Petty Cash System is a high-governance, audit-compliant
financial module engineered for construction operations. It governs cash handling
across the three primary organizational tiers:

                   ┌─────────────────────────────────────────┐
                   │           ORGANIZATION HQ ADMIN         │
                   │    • Corporate Budget Authorization     │
                   │    • Global Spending Analytics          │
                   │    • PDF Statement Generation           │
                   └────────────────────┬────────────────────┘
                                        │
                                        ▼ (Authorizes Funds)
                   ┌─────────────────────────────────────────┐
                   │             PROJECT MANAGER             │
                   │    • Request Verification               │
                   │    • Fund Disbursement (Cash/UPI/NEFT)  │
                   │    • Expense Approvals & Reconcile      │
                   └────────────────────┬────────────────────┘
                                        │
                                        ▼ (Disburses Cash)
                   ┌─────────────────────────────────────────┐
                   │          SITE CUSTODIAN SUPERVISOR      │
                   │    • Physical Receipt Confirmation      │
                   │    • On-site Field Expense Logging      │
                   │    • Bill / Invoice Camera Capture      │
                   │    • Physical Cash Box Reconciliation   │
                   └─────────────────────────────────────────┘

Key Governance Tenets:
1. Two-Person Integrity Principle:
   Funds cannot be credited to a site custodian solely by the manager or solely
   by the supervisor. Organization HQ must authorize, the Manager must disburse,
   and the Supervisor must explicitly confirm physical receipt in the field.
2. Dual Scoping (Site-Based & Supervisor-Based):
   Accounts are keyed per site (`${orgId}_${siteId}`) with supervisor custodianship.
   If a supervisor is remapped, historical site spending remains anchored to the site.
3. Complete Double-Entry Ledger:
   Every rupee added, spent, or returned generates an immutable entry in
   `pettyCashTransactions` with balance-after auditing.
4. Strict Receipt Thresholding:
   Field expenses exceeding the configured threshold (default: ₹500) mandate an
   uploaded bill/invoice image before submission.

2.1 Canonical State Machine (PettyCashStatus)
--------------------------------------------------------------------------------
Defined in: [lib/models/petty_cash_models.dart]

Lifecycle States:
- `DRAFT`                          : Created locally, not yet submitted.
- `SUBMITTED` /
  `PENDING_MANAGER_REVIEW`         : Submitted by Supervisor, awaiting Manager review.
- `REJECTED_BY_MANAGER`            : Declined by Manager with written reason.
- `PENDING_ORGANIZATION_APPROVAL`  : Verified by Manager, awaiting Org HQ authorization.
- `REJECTED_BY_ORGANIZATION`       : Declined by Org HQ.
- `APPROVED` /
  `AWAITING_DISBURSEMENT`          : Authorized by Org HQ; returned to Manager to pay.
- `DISBURSED` /
  `AWAITING_RECEIPT_CONFIRMATION`  : Manager sent funds (Cash/UPI/NEFT); awaiting field receipt.
- `RECEIVED` / `ACTIVE`            : Supervisor confirmed receipt; cash balance active.

Expense Lifecycle States:
- `PENDING_EXPENSE_REVIEW`         : Supervisor logged an expense; awaiting Manager audit.
- `EXPENSE_APPROVED`               : Manager approved expense; debited from field balance.
- `EXPENSE_REJECTED`               : Manager declined expense with written remarks.

Reconciliation, Return & Closure States:
- `REPLENISHMENT_REQUESTED`        : Top-up requested when balance reaches threshold.
- `RECONCILIATION_PENDING`         : Supervisor physical cash count awaiting Manager audit.
- `RECONCILIATION_APPROVED`        : Audit verified; cash box matches system balance.
- `DISCREPANCY_REVIEW`             : Physical cash count does not match ledger balance.
- `PENDING_RETURN_CONFIRMATION`    : Surplus funds returned to Manager; awaiting verification.
- `RETURN_CONFIRMED`               : Manager confirmed receipt of returned cash.
- `CLOSED`                         : Account deactivated or project completed.
- `CANCELLED`                      : Request cancelled by author before review.

2.2 Data Models & Entity Registry
--------------------------------------------------------------------------------
All models feature `toMap()`, `fromMap()`, and copy utilities.

1. `PettyCashAccount`:
   Represents the financial container for a site/supervisor.
   Fields: `accountId`, `orgId`, `siteId`, `siteName`, `supervisorId`, `supervisorName`,
   `managerId`, `managerName`, `totalDisbursed`, `totalSpent`, `currentBalance`,
   `maxLimit`, `thresholdLimit`, `status`, `lastDisbursedAt`, `lastExpenseAt`.

2. `PettyCashRequest`:
   Encapsulates fund requisition / allocation documents.
   Fields: `requestId`, `siteId`, `siteName`, `supervisorId`, `supervisorName`,
   `requestedAmount`, `approvedAmount`, `disbursedAmount`, `purpose`, `requestType`
   (INITIAL / REPLENISHMENT / MANUAL), `status`, `managerReviewRemarks`,
   `orgApprovalRemarks`, `paymentMode` (CASH / UPI / NEFT / CHEQUE),
   `transactionRef`, `disbursedAt`, `receivedAt`, `approvalHistory` list.

3. `PettyCashExpense`:
   Individual field expense records.
   Fields: `expenseId`, `accountId`, `siteId`, `supervisorId`, `supervisorName`,
   `amount`, `category`, `subCategory`, `description`, `vendorName`, `vendorPhone`,
   `invoiceNumber`, `receiptUrl`, `receiptStoragePath`, `status`, `expenseDate`,
   `reviewedBy`, `reviewRemarks`, `reviewedAt`.

4. `PettyCashTransaction`:
   Append-only field ledger entry.
   Fields: `transactionId`, `accountId`, `siteId`, `supervisorId`, `type`
   (CREDIT / DEBIT / RETURN), `amount`, `balanceBefore`, `balanceAfter`,
   `description`, `category`, `referenceId`, `timestamp`.

5. `PettyCashReconciliation`:
   Periodic site audit report.
   Fields: `reconciliationId`, `siteId`, `supervisorId`, `systemBalance`,
   `physicalCashCount`, `discrepancy`, `status`, `notes`, `verifiedBy`.

6. `PettyCashReturn`:
   Physical return of surplus cash.
   Fields: `returnId`, `siteId`, `supervisorId`, `returnAmount`, `reason`,
   `status`, `returnedAt`, `confirmedBy`, `confirmedAt`.

7. `PettyCashAuditLog`:
   System event audit entry tracking every role transition and state change.

  * Current Cash in Field Hand
  * Total Cumulative Disbursed
  * Total Approved Spent
  * Low Balance Alert indicators (`currentBalance <= thresholdLimit`)

Tab 7: Ledger (`_buildLedgerTab`)
- Live stream of all double-entry ledger transactions (`pettyCashTransactions`).
- Color-coded badges: Green (CREDIT), Red (DEBIT), Amber (RETURN).

Tab 8: Reports (`_buildReportsTab`)
- Category-wise spending breakdown charts (Transportation, Materials, Labour Food, etc.).
- Monthly expense trend analysis and quick CSV/PDF triggers.

Floating Action Button: "Manual Allocation"
- Allows Manager to directly inject petty cash to a supervisor/site without
  waiting for a prior supervisor request (`managerCreateManualAllocation`).

3.3 Firebase Cloud Storage Architecture for Receipts & Invoices
--------------------------------------------------------------------------------
Service: `AppStorageService`
Location: [lib/services/app_storage_service.dart]

Storage Tree:
```
firebase-storage-bucket/
└── organisation/
    └── {orgId}/
        └── petty_cash_receipts/
            ├── PCE_1740000000_555_1740000010.jpg
            └── PCE_1740000000_556_1740000020.jpg
```

Upload Mechanics:
1. `ImagePicker` compresses and selects image on mobile device.
2. `AppStorageService.uploadFile` constructs scoped reference:
   `organisation/{orgId}/petty_cash_receipts/{uniqueId}.jpg`.
3. Sets metadata: `contentType: 'image/jpeg'`.
4. Returns download URL and storage path.
5. Saved in `PettyCashExpense` document.

3.4 Atomic Transactions & Financial Concurrency Controls
--------------------------------------------------------------------------------
To prevent race conditions, double-spending, and balance corruption:

1. `supervisorConfirmAmountReceived()`:
   Runs inside `FirebaseFirestore.instance.runTransaction(...)`.
   - Reads `pettyCashRequests.doc(requestId)`.
   - Checks if already confirmed (`receivedAt != null`). If yes, exits.
   - Reads `pettyCashAccounts.doc(siteAccId)`.
   - Atomically increments `currentBalance += amount` and `totalDisbursed += amount`.
   - Writes `pettyCashTransactions` entry.
   - Commits all operations atomically.

2. `managerApproveExpense()`:
   Runs inside `FirebaseFirestore.instance.runTransaction(...)`.
   - Checks if expense was already approved.
   - Reads `pettyCashAccounts.doc(siteAccId)`.
   - Atomically updates:
     `currentBalance -= amount`
     `totalSpent += amount`
   - Creates `DEBIT` ledger transaction.
   - Commits atomically.

--------------------------------------------------------------------------------
3.5 Security Rules
--------------------------------------------------------------------------------
Firestore Security Rules ([firestore.rules]):
- All access partitioned by `/organisation/{orgId}/{collectionName}/{docId}`.
- Operations require authenticated user matching the organization namespace.

Storage Security Rules ([storage.rules]):
- `match /organisation/{orgId}/{allPaths=**}`: Read and write restricted strictly
  to authenticated users belonging to that organization.
- Unpartitioned root storage paths are denied (`allow read, write: if false`).

| Financial Event           | Sender Role    | Target Role(s) | Notification Title & Content        |
+---------------------------+----------------+----------------+-------------------------------------+
| 1. Supervisor Request     | Supervisor     | Manager & Org  | "💵 New Petty Cash Request Subm."   |
| 2. Manager Verified       | Manager        | Org HQ         | "💵 Request Forwarded to HQ"        |
| 3. Manager Rejected       | Manager        | Supervisor     | "❌ Request Declined by Manager"    |
| 4. Org HQ Authorized      | Org HQ         | Mgr & Superv   | "🏢 Request Authorized by HQ"       |
| 5. Manager Disbursed      | Manager        | Supervisor     | "💸 Cash Disbursed! Confirm Receipt"|
| 6. Supervisor Received    | Supervisor     | Manager & Org  | "✅ Cash Received in Field!"        |
| 7. Expense Submitted      | Supervisor     | Manager        | "🧾 New Site Expense for Review"    |
| 8. Expense Approved       | Manager        | Supervisor     | "✅ Site Expense Approved"          |
| 9. Expense Rejected       | Manager        | Supervisor     | "❌ Site Expense Declined"          |
| 10. Low Balance Alert     | System         | Manager        | "⚠️ Low Petty Cash Balance Alert"   |

4.2 Deep-Link Routing via NotificationRouter
--------------------------------------------------------------------------------
Source: [lib/services/notification_router.dart]

================================================================================
6. FINANCIAL INVARIANTS, ANTI-FRAUD CONTROLS & EDGE-CASE FAIL-SAFES
================================================================================

1. Double-Receipt Prevention:
   - `pettyCashRequests` uses atomic write-lock flags (`receivedAt != null`). If a
     supervisor taps "Confirm Received" multiple times or has unstable connectivity,
     only the first execution credits the account balance.

2. Negative Balance Guard:
   - `managerApproveExpense` checks whether `currentBalance >= expenseAmount`.
     If field balance is insufficient, Manager is alerted to top-up the account
     first.

3. Receipt Forgery Protection:
   - Expenses above the configurable threshold (₹500) strictly reject submission
     if `receiptUrl` is empty.

4. Immutability of Financial Ledger:
   - Documents in `pettyCashTransactions` are strictly append-only.
     Updates and deletions are denied in security rules, ensuring a tamper-proof
     audit trail for financial auditors.

5. Multi-Tenant Air-Gapping:
   - Cloud Storage paths and Firestore collections strictly mandate `organisation/{orgId}/`
     prefix. Tenant A can never view or manipulate receipts or accounts of Tenant B.
