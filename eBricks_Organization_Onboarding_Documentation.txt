1.1 Business Context & Purpose
------------------------------
eBricks is a multi-tenant enterprise resource planning (ERP) and construction management mobile 
application built on Flutter and Google Firebase. The application caters to construction developers, 
general contractors, site engineers, supervisors, and material managers.

The onboarding funnel represents the primary gateway for acquiring new organizations:
   [OrganisationLandingPage]
              |
              v
   [Step 1: Details - OrganisationRegistrationPage]
              |
              v
   [Step 2: Branding - BrandingScreen]
              |
              v
   [Step 3: Pricing - PricingScreen]
              |
              +---> [Free Trial (₹0)] --------> Direct Activation -> [OrganizationDashboard]
              |
              +---> [Paid Plan (PayU)] -------> [PayUCheckoutScreen] -> [TransactionCompletedScreen] -> [OrganizationDashboard]

This technical documentation provides an exhaustive, production-grade guide detailing every 
component, database document, API payload, encryption algorithm, UI controller, and validation 
mechanism across both the Flutter mobile client and the Node.js Firebase Cloud Functions backend.


1.2 Architectural Principles & Tenant Isolation Model
-----------------------------------------------------
1. Multi-Tenant Single-Project Architecture:
   The application shares a centralized Firebase project across multiple client organizations while 
   enforcing strict logical tenant isolation. Every organization operates within its own dedicated 
   sub-tree under the top-level collection `/organisation/{orgId}`.

2. Application Identifier Tagging (White-Label Guard):
   Because the underlying Firebase database may host companion applications (e.g., educational, 
   commercial, or partner suites), every document created by eBricks is strictly tagged with:
      - `app_id: "cst_white_label"`
      - `app_type: "cst_white_label"`
      - `is_cst_app: true`
   Queries performing global uniqueness checks (collection groups) or admin lookups filter out any 
   foreign document lacking this application signature.

3. Reactive Dynamic Theming:
   The user interface implements a reactive theme architecture via Flutter's `ValueNotifier<Color>` 
   and `ValueNotifier<String>`. Selecting a brand color or workspace name propagates instantly to the 
   root `MaterialApp` widget without requiring an application restart.

4. Resilient Staged Onboarding (Zero-Loss Funnel):
   Data entered in Steps 1 and 2 is persistently committed to Firestore as a pending record with 
   status `onboardingStep: "PAYMENT_PENDING"` and mirrored locally in `SharedPreferences`. If the user 
   kills the app, loses internet connectivity, or experiences battery exhaustion during payment, the 
   account is neither orphaned nor duplicated; upon restart, the system detects the pending registration 
   and prompts the user to resume payment seamlessly.


1.3 Namespace Strategy & Identification Standards
-------------------------------------------------
1. Organization Document ID (`orgId`):
   - Standard Namespace Prefix: `cst_` (defined in `FirestoreService.cstNamespacePrefix`)
   - Cleaning Rule: Remove all whitespace from the organization name.
   - Date Stamp: Formatted as `dd-MM-yyyy` matching the date of account initiation.
   - Formula:
     `orgId = "cst_" + cleanOrgName + "_" + dateStr`
   - Example:
     Organization Name: "Apex Builders Private Limited"
     Date Str: "27-10-2026"
     Generated `orgId`: `cst_ApexBuildersPrivateLimited_27-10-2026`

2. CST Namespace Helper Validation:
   - Evaluated via `FirestoreService.isCstOrgId(orgId)`:
     Returns true if `orgId.startsWith("cst_")` or `orgId.contains("cst")`.

3. Referral Code Generation:
   - 6-character alphanumeric uppercase string (A-Z, 0-9), verified globally unique across all 
     organizations prior to persistence via `FirestoreService.generateUniqueReferralCode()`.

3.3 Real-Time Debounced Field Validations
-----------------------------------------
Each field triggers real-time asynchronous background checks as the user types:

1. Organization Name Debounce (`_onOrgNameChanged`):
   - Cancels previous timer `_orgNameDebounce?.cancel()`.
   - Triggers `FirestoreService.isOrgNameUnique(clean)` after 200ms.
   - Evaluates:
     * Does any root `/organisation/{id}` document have `org_name` matching `clean` (case-insensitive)?
     * Does any document have `org_name` matching without spaces?
     * Does any document ID match `cst_${cleanNoSpace}_*`?
   - Displays inline status: "Organization name is available ✓" (Green) or "Organization name already exists. Please use a different name." (Red).

2. Corporate Email Debounce (`_onEmailChanged`):
   - Validates regex format locally first.
   - Triggers `FirestoreService.isGlobalEmailUnique(clean)` after 250ms.
   - Executes parallel lookups across:
     * Root `/organisation` documents
     * CollectionGroup queries: `manager`, `supervisor`, `supervisors`, `organizationUser`, `configUsers`
   - Displays inline status: "Email address is available ✓" or "Email address already registered."

3. Contact Phone Debounce (`_onPhoneChanged`):
   - Checks if length is 10 digits.
   - Triggers `FirestoreService.isGlobalPhoneUnique(clean)` after 250ms.
   - Executes parallel lookups across:
     * Root `/organisation` documents (keys: `phone`, `phoneNumber`, `mobile`, `contactNo`, `ContactNo`)
     * CollectionGroup queries: `manager`, `supervisor`, `supervisors`, `organizationUser`, `configUsers`, `customers`
   - Displays inline status: "Phone number is available ✓" or "Phone number already registered."

4. Admin Username Debounce (`_onUsernameChanged`):
   - Step A: Instant 0ms In-Memory Cache Check via `FirestoreService.isUsernameCachedAsTaken(clean)`. If found in cache, immediately marks invalid without any network round-trip.
   - Step B: Sequence Counter Guard (`_usernameValidationSeq`). Discards responses from out-of-order asynchronous keystroke responses.
   - Step C: Triggers `FirestoreService.isGlobalUsernameUnique(clean)` after 200ms.
     * Evaluates Tier 1 indexed `.limit(1)` queries with early termination (completer short-circuiting).
     * If not found, checks direct document IDs across collections.
     * Tier 2 fallback collectionGroup scan if cache is not yet warmed.
   - Displays inline status: "Username is available ✓" or "Username already exists".


3.4 Simultaneous Multi-Field Atomic Validation
----------------------------------------------
When the user taps "CONTINUE" (`_goToNextStep`):
1. Verifies form validation state (`_formKey.currentState!.validate()`).
2. Checks password equality.
3. Checks if any real-time validation indicator is flagged false.
4. Executes atomic parallel validation across all 4 parameters:
   ```dart
   final validation = await FirestoreService.validateOrganizationRegistration(
     orgName: orgName,
     email: email,
     phone: phone,
     username: username,
   );
   ```
5. Returns `OrganizationValidationResult`:
   - `isValid`: boolean
   - `errorMessage`: Specific diagnostic text if invalid
   - `isOrgNameDuplicate`, `isEmailDuplicate`, `isPhoneDuplicate`, `isUsernameDuplicate`


3.5 Pending Registration Detection & Seamless Resume Mechanism
--------------------------------------------------------------
If `validation.isValid` returns `false` due to an existing username or organization, the system does 
not simply reject the user. Instead, it inspects whether this belongs to an incomplete onboarding 
funnel:

1. Pending Inspection Query:
   ```dart
   final pendingQuery = await FirebaseFirestore.instance
       .collectionGroup('data')
       .where('username', isEqualTo: username)
       .get();
   ```
2. Detection Conditions:
   An account is classified as "Pending Registration" if:
   - `data['isSubscriptionActive'] != true`, AND
   - One of the following holds true:
     * `data['onboardingStep'] == 'PAYMENT_PENDING'`
     * `data['subscriptionPlan'] == 'Pending Selection'`
     * `data['subscriptionPlan'].isEmpty && data['paymentStatus'] == 'PENDING'`

3. User Resolution Dialog:
   If a pending registration matches, an AlertDialog is shown:
   - Title: "Pending Registration" (Blue Icon)
   - Message: "An account for '[Org Name / Username]' was already registered and is awaiting subscription payment."
   - Action Buttons: `[CANCEL]` and `[RESUME PAYMENT]`.

4. Resume Execution:
   If the user selects "RESUME PAYMENT":
   - The system retrieves `pendingData['org_name']`, `pendingData['app_name']`, and `pendingData['theme_color']`.
   - Parses the organization ID date stamp suffix.
   - Bypasses Step 2 (Branding) and routes directly to `PricingScreen` pre-populated with the saved credentials and theme color.


3.6 Client-Side Form Controllers & State Management

4.4 Theme Color System & Mathematical Shade Generation
------------------------------------------------------
File: `lib/utils/app_theme.dart`
The color chosen in Step 2 is processed mathematically through HSL (Hue, Saturation, Lightness) 
transformations to generate harmonic system shades:

1. Dynamic Background Gradients (`getBackgroundGradientColors`):
   Transforms brand color into a 4-stop light background gradient:
   - Stop 1: `Lightness = 0.95`, `Saturation = Saturation * 0.40`
   - Stop 2: `Lightness = 0.88`, `Saturation = Saturation * 0.48`
   - Stop 3: `Lightness = 0.80`, `Saturation = Saturation * 0.55`
   - Stop 4: `Lightness = 0.74`, `Saturation = Saturation * 0.60`

2. Dark Navy Accent Generation (`getDarkAccent`):
   - Formula: `HSLColor.fromColor(brandColor).withLightness(0.12).withSaturation(saturation * 0.7)`
   - Used for app bars, navigation headers, step indicators, and dark elevated buttons.

3. Card Accent Generation (`getCardAccent`):
   - Formula: Ensures contrast on dark surfaces by clamping lightness between `0.65` and `0.85`.

4. Contrast Foreground Resolution (`getForegroundFor`):
   - Evaluates luminance: `color.computeLuminance() > 0.5 ? Colors.black : Colors.white`.


4.5 Local & Remote Theme Synchronization Architecture
-----------------------------------------------------
1. ValueNotifier Reactivity:
   `AppTheme.primaryColor = ValueNotifier<Color>(defaultColor)`
   `AppTheme.appName = ValueNotifier<String>("eBricks")`
   When updated:
   - `AppTheme.updateTheme(newColor)` updates notifier and writes `newColor.toARGB32()` to 
     `SharedPreferences` key `brand_color_value`.
   - `AppTheme.updateAppName(newName)` writes to key `app_name`.

2. Remote Firestore Synchronization (`AppTheme.syncWithFirestore(orgId)`):
   Reads `/organisation/{orgId}/data/branding` and `/organisation/{orgId}` in parallel:
   - Resolves `appName` / `app_name`
   - Resolves `org_name` / `orgName`
   - Resolves `primaryColor` / `theme_color` (hex parsed via `AppTheme.hexToColor`)
   - Resolves `logoUrl` / `logo_url`


4.6 Pending Registration Persistence at Step 2
----------------------------------------------
When the user taps "SAVE CHANGES" (`_goToNextStep`):
1. Calculates target document ID:
   `cleanOrgName = widget.orgName.replaceAll(' ', '')`
   `expectedOrgId = "cst_" + cleanOrgName + "_" + widget.dateStr`

2. Re-validates registration uniqueness with an exception for self-owned pending documents.

3. Immediate Multi-Document Batch Persistence:
   Calls `FirestoreService.createPendingOrganizationRegistration(...)`:
   - Writes batch to Firestore:
     * Doc 1: `/organisation/{orgId}` (Root doc)
       `app_id`: "cst_white_label"
       `is_cst_app`: true
       `org_name`: widget.orgName
       `app_name`: appName
       `theme_color`: themeHex
       `email`: widget.email
       `phone`: widget.phone
       `username`: widget.username
       `password`: widget.password
       `role`: "Organization"
       `registrationStatus`: "COMPLETED"
       `onboardingStep`: "PAYMENT_PENDING"
       `isSubscriptionActive`: false
       `paymentStatus`: "PENDING"
       `referralCode`: referralCode
     * Doc 2: `/organisation/{orgId}/data/admin` (Admin credentials metadata)
     * Doc 3: `/organisation/{orgId}/data/branding` (`appName`, `primaryColor`, `theme_color`)
     * Doc 4: `/organisation/{orgId}/data/referralCode` (`referralCode`, `orgReferralCode`)
     * Doc 5: `/organisation/{orgId}/data/subscription` (`isSubscriptionActive: false`, `subscriptionPlan: "Pending Selection"`)
     * Doc 6: `/organisation/{orgId}/organizationUser/{username}` (User login entry)

4. Firebase Auth Sync:
   Calls `AuthService().registerWithEmail(widget.email, widget.password)`. Creates the managed 
   Firebase Auth user record.

5. Local Recovery Draft Backup:
   Writes to `SharedPreferences`:
   - `pending_org_id`
   - `pending_org_name`
   - `pending_email`
   - `pending_phone`
   - `pending_username`
   - `pending_password`
   - `pending_app_name`
   - `pending_date_str`
   - `pending_theme_color`

6. Navigation:
   Pushes `PricingScreen` with all gathered credentials.

6. PAYMENT GATEWAY INTEGRATION (PAYU HOSTED CHECKOUT)

6.1 PayU Architecture & Security Model
--------------------------------------
File: `lib/services/payu_service.dart`
File: `lib/screens/organization/payu_checkout_screen.dart`

To ensure banking-grade security and compliance with Indian payment regulations:
1. Zero Sensitive Data Storage: No credit card numbers, CVVs, or net banking passwords pass through or 
   are stored in the eBricks mobile application or database.
2. Server-Authoritative Cryptographic Signatures: Payment request parameters are signed via SHA-512 hashes. 
   Payment responses are verified against a reverse SHA-512 signature hash using the secret merchant salt.
3. Dual Verification (Client + Cloud Function): The mobile app validates the response hash locally, while 
   simultaneously triggering a Cloud Function (`verifySubscription`) that verifies the transaction server-to-server 
   and records verified payment status.


6.2 Request Hash Generation (SHA-512)
-------------------------------------
Formula:
`sha512(key|txnid|amount|productinfo|firstname|email|udf1|udf2|udf3|udf4|udf5||||||salt)`

Parameters:
- `key`         : PayU Merchant Key (`PAYU_PROD_KEY` or `PAYU_TEST_KEY`)
- `txnid`       : Generated unique transaction ID, format: `PAYU_${DateTime.now().millisecondsSinceEpoch}`
- `amount`      : Formatted strictly as 2 decimal places (e.g. `"99.00"`, `"2388.00"`)
- `productinfo` : Sanitized string, e.g. `"ApexBuilders Silver Plan (Monthly)"`
- `firstname`   : Customer/Organization name (alphanumeric only)
- `email`       : Customer email address
- `udf1`        : Organization name / identifier
- `udf4`        : `"ebricks"` (application tag)
- `udf5`        : `"ebricks_subscription"` (purpose tag)
- `salt`        : PayU Merchant Salt (`PAYU_PROD_SALT` or `PAYU_TEST_SALT`)

Implementation in `PayUService.buildPostDataAsync(params)`:
- Invokes backend Cloud Function `generatePayUHash` via HTTP POST.
- If the Cloud Function is temporarily unreachable, executes local cryptographic fallback `buildPostData(params)` 
  using Dart's `crypto` library.


6.3 Hosted Checkout Flow (WebView & PayUBridge)
-----------------------------------------------
1. HTML Form Injection:
   `PayUCheckoutScreen` creates a self-submitting HTML document in a headless string:
   ```html
   <form id="payu_form" action="https://secure.payu.in/_payment" method="post">

     <input type="hidden" name="amount" value="..." />
     <input type="hidden" name="productinfo" value="..." />
     <input type="hidden" name="firstname" value="..." />
     <input type="hidden" name="email" value="..." />
     <input type="hidden" name="phone" value="..." />
     <input type="hidden" name="surl" value="https://.../payuWebhook" />
     <input type="hidden" name="furl" value="https://.../payuWebhook" />
     <input type="hidden" name="hash" value="..." />
     <input type="hidden" name="service_provider" value="payu_paisa" />
     <input type="hidden" name="udf1" value="..." />
   ```

6.4 Response Verification & Cryptographic Signature Check
---------------------------------------------------------
Formula:
`sha512(salt|status||||||udf5|udf4|udf3|udf2|udf1|email|firstname|productinfo|amount|txnid|key)`
(If `additionalCharges` are present: `sha512(additionalCharges|salt|status|||||...)`)

Verification Steps:
1. Read `rawData['hash']` from response.
2. Re-compute hash using active merchant salt, payment status (`"success"`), amount, and credentials.
3. Compare `computedHash.toLowerCase() == rawData['hash'].toLowerCase()`.
4. If hashes do not match, payment is rejected with an error toast: "Payment signature verification failed. Please contact support."

8.1 Cloud Function: generatePayUHash
------------------------------------
- Type: HTTPS Callable Function (`functions.region("us-central1").https.onCall`)
- Purpose: Computes cryptographic request signature for PayU checkout without exposing the merchant salt.

Request Payload:
```json
{
  "data": {
    "txnid": "PAYU_1719483020000",
    "amount": 1188.00,
    "productInfo": "ApexBuilders Silver Plan (Yearly)",
    "firstName": "ApexBuilders",
    "email": "admin@apexbuilders.com",
    "phone": "9876543210",
    "merchantKey": "a912BZ",
    "environment": "production",
    "udf1": "ApexBuilders",
    "udf4": "ebricks",
    "udf5": "ebricks_subscription"
  }
}
```

Backend Logic:
1. Sanitizes inputs (strips invalid characters from names, validates email regex, formats amount to 2 decimals).
2. Reads environment configuration via `getPayUConfig(payload)`.
3. Concatenates hash string:
   `${params.merchantKey}|${params.txnid}|${amountStr}|${productInfo}|${firstName}|${email}|${udf1}|${udf2}|${udf3}|${udf4}|${udf5}||||||${salt}`
4. Calculates SHA-512 digest: `crypto.createHash("sha512").update(hashSequence).digest("hex").toLowerCase()`.
5. Prepares `postData` dictionary including service provider, surl, furl, and hash.

Response Payload:
```json

    "hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855...",
    "postData": {
      "key": "a912BZ",
      "txnid": "PAYU_1719483020000",
      "amount": "1188.00",
      "productinfo": "ApexBuilders Silver Plan Yearly",
      "firstname": "ApexBuilders",
      "email": "admin@apexbuilders.com",
      "phone": "9876543210",
      "surl": "https://us-central1-cst-whitelabel-app.cloudfunctions.net/payuWebhook",
      "furl": "https://us-central1-cst-whitelabel-app.cloudfunctions.net/payuWebhook",
      "hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855...",
      "service_provider": "payu_paisa",
      "udf1": "ApexBuilders",
      "udf4": "ebricks",
```

8.2 Cloud Function: verifySubscription
--------------------------------------
- Type: HTTPS Callable Function (`functions.region("us-central1").https.onCall`)
- Purpose: Server-side verification of payment results, Firestore subscription document activation, and invoice email dispatch.

Request Payload:
```json
{
  "data": {
    "orgId": "cst_ApexBuilders_27-10-2026",
    "txnid": "PAYU_1719483020000",
    "payuMoneyId": "403993715530123456",
    "rawData": {
      "key": "a912BZ",
      "txnid": "PAYU_1719483020000",
      "amount": "1188.00",
      "productinfo": "ApexBuilders Silver Plan Yearly",
      "firstname": "ApexBuilders",
      "email": "admin@apexbuilders.com",
      "status": "success",
      "mihpayid": "403993715530123456",
      "hash": "9f83c07e05...",
      "bank_ref_no": "20261027111222"
    },
    "planDetails": {
      "planName": "Silver",
      "planType": "Yearly",
      "amount": 1188.00,
      "payerName": "Apex Builders",
      "payerEmail": "admin@apexbuilders.com",
```

Backend Logic:
1. Idempotency Check:
   Inspects `/organisation/{orgId}/data/subscription`. If `paymentTxnId == txnid` and `isSubscriptionActive == true`,

3. Quota Resolution:

4. Database Updates (Atomic):

     * `subscriptionEndDate`: Timestamp

     * `paymentTxnId`: txnid

8.3 Cloud Function: payuWebhook (Server-to-Server IPN)
------------------------------------------------------
- Type: HTTPS onRequest (`functions.region("us-central1").https.onRequest`)
- Endpoint URL: `https://us-central1-cst-whitelabel-app.cloudfunctions.net/payuWebhook`
- Purpose: Direct webhook handler invoked asynchronously by PayU servers when payment completes.

Processing Workflow:
1. Parses URL-encoded or JSON POST body received from PayU.
2. Extracts `txnid`, `status`, `amount`, `hash`, `mihpayid`, and user-defined fields (`udf1` contains `orgName`).
3. Re-computes SHA-512 response hash.
4. Resolves the target organization document ID by scanning `organisation` root collection where 
   `org_name == udf1` or querying `data/subscription` for matching pending `txnid`.
5. Updates `/organisation/{orgId}/data/subscription` and `/organisation/{orgId}` with `paymentStatus: "SUCCESS"` 
   and `isSubscriptionActive: true`.
6. Dispatches subscription invoice email.
7. Responds to PayU with HTTP `200 OK` and renders mobile-friendly HTML bridge status.


8.4 Cloud Function: sendNewSubscriptionInvoice
----------------------------------------------
- Type: HTTPS Callable Function (`functions.region("us-central1").https.onCall`)
- Purpose: Triggered specifically for Free Trial activations (where amount is ₹0 and PayU is bypassed) 
  or manual invoice generation.
- Logic:
  * Verifies caller parameters.
  * Formats Welcome / Free Trial Activation HTML email template with organization name, login username, 
    trial duration (14 days), expiry date, and plan limit specifications.
  * Dispatches email via Nodemailer.


8.5 Cloud Function: checkSubscriptionExpiryReminders
----------------------------------------------------
- Type: Scheduled Function (Cloud Scheduler cron: `"0 4 * * *"`, runs daily at 4:00 AM UTC).
- Logic:
  1. Scans all `/organisation/{id}/data/subscription` documents where `isSubscriptionActive == true`.
  2. Compares `subscriptionEndDate` against current timestamp.
  3. Notification Thresholds:
     - 7 Days Remaining: Sends early renewal notice.
     - 3 Days Remaining: Sends urgent renewal reminder.
     - 1 Day Remaining : Sends final expiry warning.
     - Expired (< 0): Updates `isSubscriptionActive: false` and sends grace period notice.
  4. Triggers both FCM push notification and email reminder.


8.6 Transaction Idempotency & Concurrency Safeguards
----------------------------------------------------
1. PayU Transaction Keying:
   Every transaction generates a millisecond-unique transaction ID (`PAYU_${timestamp}`).
2. Deduplication Check:
   `verifySubscription` checks if the transaction ID has already been marked as `SUCCESS`. If so, it returns 
   status `ACTIVE` immediately without re-executing writes or sending duplicate invoices.
3. Firestore Set Options Merge:
   All updates use `SetOptions(merge: true)` ensuring that concurrent updates do not overwrite concurrent 
   changes to unrelated subcollections or fields.

9.3 Cross-Application Isolation & Security Rules (firestore.rules)
------------------------------------------------------------------
File: `firestore.rules`
```javascript
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    function isCstDoc(data) {
      return data.app_id == 'cst_white_label' || data.appType == 'cst_white_label' || data.is_cst_app == true;
    }

    function isCstOrg(orgId) {
      return orgId.matches('cst_.*') || orgId.matches('.*cst.*');
    }

    match /organisation/{orgId} {
      allow read: if isCstOrg(orgId) || isCstDoc(resource.data) || resource == null;
      allow create: if isCstOrg(orgId) || isCstDoc(request.resource.data);
      allow update, delete: if isCstOrg(orgId) || isCstDoc(resource.data);

      match /{collectionName}/{docId} {
        allow read, write: if collectionName != 'vehicleMovements' && (isCstOrg(orgId) || request.auth != null);

        match /{nestedSub=**} {
          allow read, write: if collectionName != 'vehicleMovements' && (isCstOrg(orgId) || request.auth != null);
        }
      }
    }

    match /{path=**}/data/{docId} {
      allow read: if resource.data.app_id == 'cst_white_label' || resource == null;
      allow write: if request.resource.data.app_id == 'cst_white_label';
    }

    match /{path=**}/manager/{docId} {
      allow read: if true;
    }

    match /{path=**}/supervisor/{docId} {
      allow read: if true;
    }
  }
}
```

11. EDGE CASES, ERROR RECOVERY & APP CLOSURE BEHAVIOR
====================================================================================================

11.1 App Killed / Closed During Registration
--------------------------------------------
Problem Statement:
What happens if the user kills the mobile app, experiences an OS crash, or runs out of battery:
- Case 1: App killed during Step 1 (before tapping Continue):
  Nothing was written to Firestore. Form state is abandoned. No orphan records exist.
- Case 2: App killed during Step 2 (before tapping Save Changes):
  Nothing was written to Firestore. No orphan records exist.
- Case 3: App killed during Step 3 or during PayU Checkout (after Step 2 was completed):
  The organization document was already committed to Firestore with:
  `onboardingStep: "PAYMENT_PENDING"`, `isSubscriptionActive: false`.
  The local draft was saved to `SharedPreferences` (`pending_org_id`, etc.).

Recovery Behavior:
1. When user reopens the app:
   - If user visits `/orgRegistrationForm` and types their username or organization name, the real-time 
     check triggers pending detection.
   - An alert dialog appears:
     "Pending Registration - An account for '...' was already registered and is awaiting subscription payment."
   - Tapping "RESUME PAYMENT" fetches the pending document from Firestore, skips Steps 1 and 2, and 
     navigates directly to `PricingScreen` with the saved theme and credentials pre-loaded.
2. In `PricingScreen.initState()`:
   - When opened, `_checkExistingSubscriptionStatus()` immediately checks if payment was already completed 
     in the background (e.g., via asynchronous PayU webhook).
   - If subscription is already active, redirects directly to `OrganizationDashboard`.


11.2 Payment Cancellation, Gateway Dropouts & Failed Transactions
-----------------------------------------------------------------
1. User Cancels in PayU Gateway:
   - PayU returns status `"cancel"`, `"cancelled"`, or `"user_cancelled"`.
   - `PayUCheckoutScreen` intercepts cancellation and pops back with `PayUResult(isSuccess: false, errorMessage: "Payment was cancelled or failed.")`.
   - `PricingScreen` displays a floating error toast: "Payment was cancelled or failed. Please try again."
   - Account remains safely in `PAYMENT_PENDING` state. User can retry immediately with another card, UPI, 
     or change to a different billing tier.

2. Insufficient Funds / Bank Decline:
   - PayU returns `status: "failure"` with bank error message.
   - Screen remains on `PricingScreen`, displaying the specific error message returned by the gateway.


11.3 Network Dropouts & Offline Cache Behavior
----------------------------------------------
1. Offline During Step 1:
   - Debounce checks fail with "Error validating [field]. Please check network."
   - Form submission blocks until network connectivity is restored via `ConnectivityWrapper`.
2. Offline During PayU Hash Generation:
   - If Cloud Function times out (8 seconds), `PayUService` falls back to local SHA-512 calculation using 
     in-app cryptographic salts.
3. Offline During Step 3 Finalization:
   - Cloud Firestore enables offline disk persistence. Writes to `organisation/{orgId}` and `data/subscription` 
     are queued locally and synced automatically the moment data connectivity resumes.


11.4 Duplicate Registration Prevention & Race Condition Handling
----------------------------------------------------------------
1. Simultaneous Registrations with Same Name / Username:
   - Tier 1 and Tier 2 indexed queries check root organizations, collection groups (`manager`, `supervisor`, 
     `organizationUser`, `configUsers`), and direct document paths.
   - Case-Insensitivity: All usernames and emails are converted to lower-case prior to querying and saving.
   - Whitespace Immunity: Organization names are stripped of whitespace and compared against `cst_${noSpace}_*`.


11.5 Cryptographic Signature Mismatch Handling
----------------------------------------------
- If a man-in-the-middle, proxy, or compromised client attempts to tamper with the amount, transaction ID, 
  or response status, the reverse SHA-512 signature hash will fail:
  `computedHash != receivedHash`
- Result:
  * Client refuses to activate subscription.
  * Backend flags transaction as `FAILED_HASH_MISMATCH`.
  * Subscription is NOT activated.
  * Toast displays: "Payment signature verification failed. Please contact support."
