2. ROLES, ACTORS & SEPARATION OF DUTIES
================================================================================
Three distinct roles participate in the system:

1. SUPERVISOR (Site Custodian / Field Staff)
   - Requests initial petty cash fund or replenishment for assigned sites.
   - Confirms physical cash receipt from Manager.
   - Spends from active funds and submits daily expenses (with photo receipts).
   - Counts and submits physical cash reconciliation periodically.
   - Surrenders unspent cash via Cash Return.

2. MANAGER (Project / Operations Manager)
   - Reviews supervisor petty cash requests and forwards them to HQ.
   - Can proactively allocate petty cash directly to a site/supervisor.
   - Disburses cash physically or electronically to the supervisor.
   - Reviews each submitted expense (verifies receipts >= Rs 500).
   - Approves expenses (deducts available balance, posts to ledger).
   - Rejects invalid expenses (releases reserved balance without deduction).
   - Confirms receipt of physical cash returns.
   - Monitored by Separation of Duties: Cannot approve own requests/expenses!

3. ORGANIZATION (HQ Admin / Finance Department / Executive)
   - Highest approval authority.
   - Authorizes or rejects petty cash requests forwarded by Manager.
   - Can adjust approved amount during authorization.
   - Views organization-wide master ledgers, site-by-site analytics, and audits.
   - Generates monthly financial compliance reports and exports PDFs.

3. CANONICAL STATUS STATE MACHINES
================================================================================
All status strings are uppercase, normalized with underscores:

A. REQUEST STATUSES:
   - DRAFT
   - SUBMITTED
   - PENDING_MANAGER_REVIEW
   - REJECTED_BY_MANAGER
   - PENDING_ORGANIZATION_APPROVAL
   - REJECTED_BY_ORGANIZATION
   - APPROVED
   - AWAITING_DISBURSEMENT
   - DISBURSED
   - AWAITING_RECEIPT_CONFIRMATION
   - RECEIVED (Active in Field)
   - ACTIVE
   - CLOSED
   - CANCELLED

B. EXPENSE STATUSES:
   - PENDING_EXPENSE_REVIEW (Initial state on submit, funds reserved)
   - EXPENSE_APPROVED (Manager approved, balance deducted, posted to ledger)
   - EXPENSE_REJECTED (Manager declined, funds released from reserve)

C. RECONCILIATION STATUSES:
   - RECONCILIATION_PENDING (Physical count matches expected balance)
   - DISCREPANCY_REVIEW (Physical cash != expected cash, requires review)
   - RECONCILIATION_APPROVED (Manager/HQ verified count)

D. RETURN STATUSES:
   - PENDING_RETURN_CONFIRMATION (Supervisor handed over physical cash)
   - RETURN_CONFIRMED (Manager/HQ confirmed receipt, ledger updated)
   - RETURN_REJECTED (Disputed return)

ALLOWED TRANSITIONS MATRIX:
   DRAFT                          -> SUBMITTED | PENDING_MANAGER_REVIEW | CANCELLED
   SUBMITTED                      -> PENDING_MANAGER_REVIEW | PENDING_ORGANIZATION_APPROVAL | REJECTED_BY_MANAGER | CANCELLED
   PENDING_MANAGER_REVIEW         -> PENDING_ORGANIZATION_APPROVAL | APPROVED | REJECTED_BY_MANAGER | CANCELLED
   PENDING_ORGANIZATION_APPROVAL  -> APPROVED | AWAITING_DISBURSEMENT | DISBURSED | AWAITING_RECEIPT_CONFIRMATION | REJECTED_BY_ORGANIZATION | CANCELLED
   APPROVED                       -> AWAITING_DISBURSEMENT | DISBURSED | AWAITING_RECEIPT_CONFIRMATION | CANCELLED
   AWAITING_DISBURSEMENT          -> DISBURSED | AWAITING_RECEIPT_CONFIRMATION | CANCELLED
   DISBURSED                      -> AWAITING_RECEIPT_CONFIRMATION | RECEIVED | ACTIVE
   AWAITING_RECEIPT_CONFIRMATION  -> RECEIVED | ACTIVE
   RECEIVED                       -> ACTIVE | CLOSED
   ACTIVE                         -> REPLENISHMENT_REQUESTED | RECONCILIATION_PENDING | CLOSED
   PENDING_EXPENSE_REVIEW         -> EXPENSE_APPROVED | EXPENSE_REJECTED
   RECONCILIATION_PENDING         -> RECONCILIATION_APPROVED | DISCREPANCY_REVIEW
   DISCREPANCY_REVIEW             -> RECONCILIATION_APPROVED | CLOSED

4. COMPLETE STEP-BY-STEP WORKFLOWS
================================================================================

--------------------------------------------------------------------------------
FLOW A: PETTY CASH REQUEST LIFECYCLE (5-STEP STANDARD FLOW)
--------------------------------------------------------------------------------
Step 1: Supervisor Submits Request
  - Input: siteId, siteName, requestedAmount, reason, requiredDate, documentUrl,
           optional linkedSitePaymentId.
  - Action: Creates document in `pettyCashRequests` with status: 'PENDING_MANAGER_REVIEW'.
  - Current Step = 1.
  - Notification sent to Manager.
  - Balance Impact: 0.

Step 2: Manager Reviews & Forwards
  - Options:
    a) Forward to HQ: Updates status to 'PENDING_ORGANIZATION_APPROVAL', currentStep = 2,
       managerReviewRemarks = remarks. Notification sent to Org.
    b) Reject: Updates status to 'REJECTED_BY_MANAGER', currentStep = -1,
       rejectionReason = reason (mandatory!). Notification sent to Supervisor.

Step 3: Organization (HQ) Authorizes
  - Options:
    a) Authorize: Enters approvedAmount, remarks. Updates status to
       'AWAITING_RECEIPT_CONFIRMATION' (or 'AWAITING_DISBURSEMENT'),
       currentStep = 4, orgApprovedBy, orgApprovedAt.
    b) Reject: Status to 'REJECTED_BY_ORGANIZATION', currentStep = -1,
       rejectionReason = reason.

Step 4: Manager Disburses Funds (if separate disbursement step)
  - Enters disbursementAmount, disburseMethod (Cash / Transfer).
  - Status updated to 'AWAITING_RECEIPT_CONFIRMATION'.

Step 5: Supervisor Confirms Receipt (CRITICAL ATOMIC STEP)
  - The supervisor physically verifies money in hand.
  - Clicks "Confirm Amount Received".
  - Runs in a Firestore Atomic Transaction:
    1. Reads Request: Checks if already confirmed (`receivedAt != null`). If yes, exits.
    2. Reads Site Account: `/organisation/{orgId}/pettyCashAccounts/{orgId}_{siteId}`.
    3. Calculates new balances:
       newTotalAllocated = prevTotalAllocated + receivedAmount
       newTotalReceived  = prevTotalReceived + receivedAmount
       newAvailableBal   = prevAvailableBal + receivedAmount
       newCycleAllocated = (isReplenishment ? prevCycleAllocated + receivedAmount : receivedAmount)
    4. Updates Request Document:
       status = 'RECEIVED'
       receivedAmount = receivedAmount
       receivedAt = serverTimestamp()
       remainingBalance = receivedAmount
       currentStep = 5
    5. Updates Account Document:
       totalAllocated = newTotalAllocated
       totalReceived  = newTotalReceived
       availableBalance = newAvailableBal
       currentCycleAllocated = newCycleAllocated
       status = 'ACTIVE'
    6. Writes Immutable Ledger Transaction:
       transactionType = isReplenishment ? 'REPLENISHMENT' : 'INITIAL_FUND'
       amount = receivedAmount
       previousBalance = prevAvailableBal
       newBalance = newAvailableBal
       status = 'POSTED'
    7. Updates linked site supervisor payments/entries:
       fundedViaPettyCash = true
    8. Writes Audit Log:
       action = 'CASH_RECEIPT_CONFIRMED'
  - Post-transaction: Triggers notifications & project cost recalculation.

--------------------------------------------------------------------------------
FLOW B: TWO-STAGE EXPENSE LIFECYCLE (SUBMIT -> APPROVE -> POST)
--------------------------------------------------------------------------------
Stage 1: Supervisor Submits Expense
  - Validation:
    * amount > 0
    * description is required
    * if amount >= Rs 500 (threshold): receiptUrl is MANDATORY, OR supervisor
      must provide written `noReceiptReason`.
    * amount <= account.spendableBalance (where spendableBalance = availableBalance - reservedBalance)
  - Execution (Atomic):
    1. Creates document in `pettyCashExpenses`:
       status = 'PENDING_EXPENSE_REVIEW'
       postedToLedger = false
    2. Updates Account:
       reservedBalance += amount
    3. Writes Audit Log: 'EXPENSE_SUBMITTED'
  - Balance Impact:
    * Available Balance: UNCHANGED
    * Reserved Balance: INCREASED by amount
    * Spendable Balance: DECREASED by amount (prevents double-spending!)

Stage 2A: Manager Approves Expense (Atomic Transaction)
  1. Validates: amount <= account.availableBalance.
  2. Account Balance Updates:
     newAvailableBalance = availableBalance - amount
     newTotalSpent       = totalSpent + amount
     newReservedBalance  = reservedBalance - amount
  3. Low Balance Trigger Check:
     threshold = currentCycleAllocated * 0.10 (10% threshold)
     if newAvailableBalance <= threshold -> flag lowBalanceTriggered = true, send alert.
  4. Creates Ledger Entry in `pettyCashTransactions`:
     transactionType = 'EXPENSE_APPROVED'
     amount = amount
     previousBalance = availableBalance
     newBalance = newAvailableBalance
     status = 'POSTED'
  5. Updates Expense Document:
     status = 'EXPENSE_APPROVED'
     postedToLedger = true
     reviewedBy = managerName
     transactionId = createdTxnId
     receiptVerified = true
  6. Writes Audit Log: 'EXPENSE_APPROVED'
  7. Async: Recalculates Site/Project financials.

Stage 2B: Manager Rejects Expense (Atomic Transaction)
  1. Updates Expense Document:
     status = 'EXPENSE_REJECTED'
     rejectionReason = reason (mandatory!)
     reviewedBy = managerName
  2. Account Balance Updates:
     reservedBalance = max(0, reservedBalance - amount)
     (availableBalance is NOT touched!)
  3. Writes Audit Log: 'EXPENSE_REJECTED'
  4. Notifies Supervisor.

--------------------------------------------------------------------------------
FLOW C: PHYSICAL CASH RECONCILIATION WORKFLOW
--------------------------------------------------------------------------------
1. Expected Cash Calculation:
   expectedCash = totalReceived - totalSpent - totalReturned
2. Supervisor inputs actual counted cash: `physicalCash`.
3. System calculates difference:
   difference = physicalCash - expectedCash
4. If |difference| > 0.01:
   - differenceReason is MANDATORY.
   - Status set to 'DISCREPANCY_REVIEW'.
   Else:
   - Status set to 'RECONCILIATION_PENDING'.
5. Saved in `pettyCashReconciliations`.
6. Manager / HQ reviews and approves or resolves discrepancy.

--------------------------------------------------------------------------------
FLOW D: CASH RETURN WORKFLOW (PHYSICAL CASH SURRENDER)
--------------------------------------------------------------------------------
1. Supervisor surrenders unspent cash:
   - returnAmount <= account.availableBalance.
   - Reason & optional handover proof document.
   - Saved in `pettyCashReturns` with status: 'PENDING_RETURN_CONFIRMATION'.
2. Manager / HQ confirms physical cash received (Atomic Transaction):
   - Updates Account:
     availableBalance -= returnAmount
     totalReturned += returnAmount
   - Creates Ledger Transaction:
     transactionType = 'CASH_RETURN'
     amount = returnAmount
     status = 'POSTED'
   - Updates Return Document:
     status = 'RETURN_CONFIRMED'
     receivedBy, receivedAt, transactionId
   - Writes Audit Log: 'CASH_RETURN_CONFIRMED'.

--------------------------------------------------------------------------------
FLOW E: PROACTIVE MANAGER ALLOCATION WORKFLOW
--------------------------------------------------------------------------------
1. Manager can proactively fund a site directly from manager dashboard.
2. Manager submits: siteId, supervisorId, amount, reason.
3. System creates request in `pettyCashRequests` with:
   requestType = 'MANUAL_MANAGER'
   requestSource = 'MANUAL_MANAGER'
   status = 'PENDING_ORGANIZATION_APPROVAL' (currentStep = 2)
   managerReviewedBy = managerName
4. Jumps straight to HQ Approval (Step 3).

================================================================================
5. BALANCE ARITHMETIC & LOW-BALANCE ENGINE
================================================================================

Account Balance Definitions:
  1. TOTAL ALLOCATED (totalAllocated) = Cumulative total granted to site/account.
  2. TOTAL RECEIVED (totalReceived)   = Cumulative total confirmed received by supervisor.
  3. TOTAL SPENT (totalSpent)         = Cumulative sum of APPROVED expenses posted.
  4. TOTAL RETURNED (totalReturned)   = Cumulative sum of confirmed cash returns.
  5. AVAILABLE BALANCE (availableBalance) =
     totalReceived - totalSpent - totalReturned
  6. RESERVED BALANCE (reservedBalance) =
     Sum of all submitted expenses currently in 'PENDING_EXPENSE_REVIEW'.
  7. SPENDABLE BALANCE (spendableBalance) =
     Math.max(0, availableBalance - reservedBalance)
     * Supervisor CANNOT submit new expenses if expenseAmount > spendableBalance!
  8. LOW BALANCE THRESHOLD AMOUNT =
     if (configuredMinimumBalance > 0) return configuredMinimumBalance;
     base = (fundLimit > 0) ? fundLimit : currentCycleAllocated;
     return base * (lowBalanceThresholdPercent / 100.0); // Default is 10%
  9. LOW BALANCE FLAG:
     isLowBalance = (totalAllocated > 0) && (availableBalance <= lowBalanceThresholdAmount);

8. ATOMICITY, TRANSACTIONS & IDEMPOTENCY RULES
================================================================================
1. ALL BALANCE MUTATIONS MUST RUN IN FIRESTORE TRANSACTIONS:
   - Reading account doc -> calculating new balance -> writing account & ledger.
   - Never write to account balances using client-side arithmetic without transactions!
2. IDEMPOTENCY KEYS:
   - For Cash Receipt: `RECV_{requestId}_{amount}`
   - For Expense Submit: `EXP_{supervisorId}_{timestamp}_{amount}`
   - For Expense Approval: `EXP_APPROVED_{expenseId}`
   - For Cash Return: `RET_CONFIRMED_{returnId}`
3. RECEIPT THRESHOLD:
   - Expenses >= Rs 500 MUST either have `receiptUrl` OR `noReceiptReason`.
4. SEPARATION OF DUTIES:
   - A manager or org admin who created an allocation or request CANNOT approve it.
   - `actorId.toLowerCase() != requesterId.toLowerCase()`.
